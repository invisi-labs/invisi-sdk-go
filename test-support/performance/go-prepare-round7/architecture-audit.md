Target contracts: initialize static epoch-scoped config/capability; prepare current nonce/state and business intent; quote fee-only/budgeted transformation or explicit NeedsReprepare; authorize/prove/finalize complete artifacts; submit completed packet plus finite current network/requirements fence/atomic persistence/wire; recover saved packet/status. ## Conclusion

Not yet fully stage-minimal. The initialized, ordinary self-contained Shield success path is deliberately slimmer, but that does not establish the same separation for Transfer, Credit, manual export, custom readers, restore, or invalidated initialization. Main remaining architectural debts are quote reentering preparation / selecting funding terms, signing exports that acquire chain state, provenance generation inside submit, and Credit submission repeating full validation. Fresh execution state checks are legitimate final-gate obligations and must not simply be deleted.

## Actionable findings

1. **P2: Quote owns funding-term acquisition and general preparation.** Rust quote silently selects a fresh funding nonce when selected_funding_terms is false (`src/sdk/prepared_broadcaster.rs:877–894`), then installs it in repriced candidate (`:1016–1018`). TS clones original intent and calls reprepare (`broadcaster-preparation.ts:327–341`); omitted nonce flows into PrepareCommon.funding's live read (`prepare-common.ts:155–163`). The quote is therefore not solely a price/model transformation, and repeated quote can produce a different authorization prerequisite. Bounded next step: explicit prepare/selectFundingTerms result consumed unchanged by repricing, with distinct explicit reprepare if new inputs or funding prerequisite is needed. Preserve legitimate fee-driven input reselection and gross funding/permit convergence; do not force a fake pure quote if it changes input facts.

2. **P2: Export/sign responsibility differs by path and SDK.** Rust non-fast export_funding_authorization performs a live snapshot, nonce and canonicality (`sdk.rs:2642–2660`); with_funding_signature opens that gate and then another snapshot (`:2670,2681`). TS legacy equivalent does deployment/head/nonce/canonicality, while managed required plan is local (`operation-execution.ts:132–151`). This makes seemingly identical export APIs latency/failure dependent on restored snapshot/capability. Separate pure request construction + signature binding from explicit refresh/validate authorization prerequisites; contract-wallet signature verification remains a distinct potentially live verifier, with latest execution validation at submit.

3. **P2: Submit still builds missing provenance rather than consuming completed evidence.** TS Operation first send invokes #proveProvenance after current requirements (`Operation.ts:592–600`); standalone PreparedTransaction does likewise (`PreparedTransaction.ts:206–213`). Rust freeze_broadcaster_evidence creates missing capability and calls prove_provenance, and normal submit invokes freeze (`prepared_broadcaster.rs:1228–1248`; `session/operation.rs:292–295`). Signed quote already authenticates provenance_required. Put sidecar creation into explicit proof/finalize preparation before freeze; final submit should compare current requirements to frozen signed requirements and reject changes. A convenience orchestration method may still compose those stages, but should not hide them in the primitive send operation. Restore with missing capability should explicitly reattach/reprove, not silently expand the normal send path.

4. **P2: Credit retains repeated broad gates instead of one dynamic final gate.** Standalone TS Credit draw/initial-payment runs validateSubmission before requirements/proof and once again after persistSchedule (`PreparedTransaction.ts:202–239`). Managed TS already runs assertCreditPeriodCurrent in its full gate (`submission-validation.ts:179–181`) yet immediately reads another head for Credit period (`Operation.ts:604–610`). Rust Credit submit computes live calldata pre-commit at `session/operation.rs:304` and again `:426`; final prepared Credit submission captures another snapshot (`src/sdk/prepared_credit_broadcaster.rs:314`). The first early gate may be useful as fail-fast policy, but should not duplicate every mutable read. Use local immutable packet construction/evidence validation pre-commit and one full pinned live gate after persistence; preserve the final time check needed across expensive proof/persistence.

5. **P2 architecture / P1 candidate requiring targeted reproduction: TS managed final network guard ends before durable persistence.** `validateOperationSubmission` returns and closes network scope (`submission-validation.ts:106–110,142–149`), then Operation awaits store.transaction (`Operation.ts:604,613–635`) and sends (`:639`). A slow/async store commit or endpoint/policy change during commit is outside that guard. Rust explicitly commits first and then performs entry/final delegated network fence (`session/operation.rs:474–490`; prepared_broadcaster.rs:1367–1372,1493–1496). Next bounded test: block store persistence, change native provider chain/policy, release persistence, assert transport does not fire. Carry frozen-packet authority through journal and acquire final finite network fence after commit. Do not move the *entire* full validation after commit without preserving retry/refusal journal semantics.

6. **P3: Rust confirmation repeats snapshot validation through nested layers.** Operation.confirmation calls chain.snapshot then chain.transaction_confirmation (`session/operation.rs:110–111`); InitializedRpcChainState.transaction_confirmation calls snapshot, then underlying RpcChainState.transaction_confirmation calls snapshot again (`initialized.rs:144–146`; sdk.rs:818–820). Raw underlying snapshot includes runtime code/hash check even with valid initialized wrapper (`sdk.rs:837–842`). This is an unambiguous layering duplication, though outside send critical path. Establish one confirmation owner for current chain fence and expose a lower raw confirmation read.

## Necessary final checks / guardrails

- Preserve current network identity and mutable service requirements/halt status. Rust submission_requirements intentionally calls broadcaster_getStatus and validates version/chain/signer/recipient/current halt/provenance (`crates/invisi-sdk-rpc/src/broadcaster.rs:687–712`); it is not redundant static support discovery.
- Preserve current deadlines, nonce, spendability/root acceptance, Credit state/period, balance/allowance and relevant contract wallet validity for manual/private/Credit/nondelegated paths. Delegating ordinary Shield execution to bound broadcaster/contract is a specific policy capability, not proof that all other paths can omit those reads.
- Preserve canonical fences around a pinned set; custom reader behavior and unsupported hash fallback must remain fail-closed. Do not memoize mutable facts across first-send persistence or a new authorization.
- Static code/version/registry/support can be initialized only with explicit validated lifetime. TS custom/prototype-overridden/revocation-scoped/no-identity reader bypasses deployment receipt (`preparation-reads.ts:75–85`); TS Credit submission bypasses reusable deployment branch (`submission-validation.ts:169–176`). Rust invalidated receipt permanently falls back to full legacy snapshot (`initialized.rs:64–66`). These are conservative fallback obligations, not unconditional remove-check findings.
- Initialization invalidation must never erase attempted packet/reservations. Existing uncertain replay paths correctly use immutable authority without fresh quote/nonce/repricing; keep that ordering. No evidence in the reviewed paths that retiring initialization itself overwrites attempted obligations.
- No unexpected live property getter found in the reviewed code: Rust provenance_mode is local field access (`rpc/broadcaster.rs:645–646`), initialization_token serializes local prepared snapshot (session operation.rs:1712–1716). TS getBroadcasters is explicitly async and may discover if not initialized; export methods above do contain path-dependent network I/O. This is not an exhaustive audit of every getter in all packages.
