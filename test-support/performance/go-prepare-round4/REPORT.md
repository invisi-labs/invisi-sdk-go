# Go 预热去重：首笔完整成本对比

本轮在原有每笔 7 次请求的基础上，降低 `InitializeShieldPreparation` 的额外成本。普通默认或自定义服务客户端从 6 次降为 4 次；显式选择 `protocolrpc.ClientOptions{UseNativeHTTPTransport: true}`，且同一在线构造器的服务核验仍有效时，降为 3 次。每笔正常交易仍为 7 次。没有 rebase develop、提交、部署或真实广播，也没有修改 TS/Rust。

## 6 次请求分别如何处理

适用场景：空钱包、普通签名资金 Shield、原生链绑定、无可选注册表、节点支持 EIP-1898。广播器初始化原有的 3 次另计。

| 预热请求 | 修改前 | 普通客户端 | 原生传输并有有效构造核验 |
|---|---:|---:|---:|
| Protocol 服务 `invisi_getDeployment` | 1 | 1 | 0 |
| 最新区块 `eth_getBlockByNumber` | 1 | 1 | 1 |
| 实时网络 `eth_chainId` | 1 | 1 | 1 |
| Core 代码 `eth_getCode` | 1 | 0 | 0 |
| Core `VERSION()`，`eth_call:ffa1ad74` | 1 | 0 | 0 |
| Token 代码，区块哈希并要求 canonical | 1 | 1 | 1 |
| **额外预热总计** | **6** | **4** | **3** |

Core 代码哈希、版本及可选不可变注册表绑定，复用同一个 `chain.Protocol`、原生 `*chain.HTTPBinding` 和连接 epoch 上已经核验的初始化结果。最新头和 Token 证据仍实际读取；不会把初始化时的 Core 核验冒充成在新历史区块的 Core 观察。预热还会本地拒绝早于 Core 部署高度的区块。完整钱包同步仍使用按区块固定的 recorder，并实际核验选定服务。

服务查询只在显式选择 SDK 私有传输且在线构造结果仍有效时复用；默认及自定义客户端保留原来的传输策略与新鲜服务查询。新选项不能与 `HTTPClient` 同时使用，固定传输支持连接池、标准 TLS、环境代理、复制的请求头及原有重定向拒绝。新增字段兼容带字段名的 `ClientOptions` 字面量；外部无字段名的结构体字面量需要更新。

公共 `GetDeployment` 始终发请求。客户端或其 provider 克隆开始另一次部署查询时，旧服务观察立即失效，包括失败或取消的查询。静态地址配置和 JSON 不能创建服务观察。换 epoch、换来源或离线恢复会重新核验；旧构造观察失效后，后续显式预热继续实际核验服务，直到新的在线构造提供可复用观察。普通调用的重叠查询仍可返回匹配的部署数据，但过时的观察不能授予准备权限。

## 同一套实际 HTTP 诊断

对修改前的冻结源码与最终源码分别构建独立二进制，使用完全相同的诊断驱动。3 个独立 fixture，每个 fixture 复用同一会话连续执行两笔交易，分别实际选择并消费 nonce 7、14，验证第二笔不修改第一笔日志。所有冷构造、初始化、失败探测均计数；到最内层传输拒绝广播为止，拒绝的写请求没有出站，不冒充一次已发送的网络请求。

这是原生 SDK 通过真实 HTTP/TLS 访问本地可控服务的对比，每次响应固定延迟 20 ms，所有计时组串行执行并避开完整测试负载。它验证 SDK 发出的请求和成本差异，不能代表公网节点、App 或真实成交耗时。默认服务对比的前后版本均使用同一普通 HTTP 端点；relay 均使用同一 TLS fixture。自定义服务客户端对照使用其自己的 TLS 客户端，其绝对时间单列。

耗时单位为 ms，均为 3 个 fixture 的中位数。首笔完整耗时先在各 fixture 内相加，再取中位数，不能用各阶段中位数直接相加。

| 组别 | 冷构造请求 | 初始化请求（含原有 3 次） | 首笔交易请求/耗时 | 第二笔请求/耗时 | 首笔含全部启动请求/耗时 |
|---|---:|---:|---:|---:|---:|
| 修改前 | 7 | 9 | 7 / 189.27 | 7 / 187.22 | 23 / 545.71 |
| 修改后：默认服务客户端 | 7 | 7 | 7 / 188.42 | 7 / 186.54 | 21 / 497.20 |
| 修改后：显式原生传输 | 7 | 6 | 7 / 188.52 | 7 / 190.68 | 20 / 477.26 |
| 自定义服务客户端对照 | 7 | 7 | 7 / 178.77 | 7 / 186.75 | 21 / 482.58 |
| 原生传输，哈希选择器不支持 | 7 | 8 | 7 / 191.30 | 7 / 186.80 | 22 / 522.89 |

默认模式的首笔完整成本 **23→21 次，545.71→497.20 ms**；原生传输模式 **23→20 次，545.71→477.26 ms**。两笔合计含全部启动成本的请求数分别为 **30→28 / 27**。初始化阶段（含原有 3 次广播器初始化）的中位数为 **200.90→155.06 / 131.84 ms**。交易本身的 7 次与耗时基本不变，本轮收益在启动和预热。

所有 5 组、共 210 个阶段记录通过独立核对：每组 3 个 fixture、每个两笔；修改前后诊断驱动逐文件 SHA-256 一致，修改后全部源码与冻结二进制输入一致。失败的选择器探测也在请求数中。

EIP-1898 不支持对照也将失败的哈希选择器探测计入：原生传输预热为 5 次（实时头、网络、失败探测、数字高度 Token 代码、最终头围栏），加上原有广播器初始化 3 次后共 8 次。后续两笔仍各 7 次。额外的钱包检查点和可选注册表不属于本次数量承诺。

交易内的 7 次仍为：准备阶段网络和最新 nonce 2 次、报价 estimate/getQuote 2 次、发送前网络/广播器状态/最终网络 3 次。资金签名本地完成。没有缓存 nonce，没有去掉钱包代次、检查点、Token、真实网络、连接 epoch、准备票据和第一次发送围栏。

## 正确性与失败恢复

新测试覆盖预热精确请求数、默认/自定义策略、源服务失败与取消、provider 克隆撤销、重叠查询、请求头复制、静态部署配置和离线恢复不能伪造来源证明。独立审查发现并修复了两类问题：旧初始化延迟恢复可能撤销新结果，以及准备头低于 Core 部署高度。三个先失败的回归用例验证了修复；共享短临界区只安排票据和服务查询代次，HTTP 在解锁后执行。被后来的捕获替代的完整同步保留已提交的钱包结果。

现有版本 2 日志、旧 SDK 拒绝不兼容恢复、原子持久化、落盘后首次发送围栏、未知提交结果的原包重放、已知 ID 的只查状态、服务/网络失效后的恢复保护均保留。冻结包恢复不要求重新取得准备缓存，也不会改签或切换原广播器。
