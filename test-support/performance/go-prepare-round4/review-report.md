## Findings on the initial candidate

1. **P2. A superseded capture can retire the successful newer capture.** In session/shield_preparation_anchor.go, line 124, an initializer returning from the wallet metadata read can start VerifyDeployment after a later initializer has already published its receipt. On a default, custom or restored client the older call advances the shared service generation at rpc/discovery.go, line 71. Its own ticket check eventually fails, but the winning receipt now fails its service check at session/shield_preparation_anchor.go, line 54. The next PrepareShield for the winning token returns an error even if both deployment responses matched. The full-refresh check at session/shared_state.go, line 232, also leaves an interval before it starts VerifyDeployment. Wallet ticket admission and the start of the service observation need a common ordering. Rejected earlier work should leave the winning observation usable. There is a related result-order issue at session/shield_preparation_anchor.go, line 194. A full refresh whose service request began first and whose wallet ticket was later superseded returns a service error after committing state because that check precedes the wallet ticket check. The caller at session/shared_state.go, line 288, deliberately tolerates a superseded wallet ticket. Regression coverage should interleave the older initializer's metadata read and the older refresh's final publication with a successful newer capture.
2. **P2. A predeployment head can now be promoted.** The latest-header conversion at session/shield_preparation_anchor.go, line 133, accepts a capture height below the authenticated Core deployment's FromBlock. With an empty wallet, a lagging backend or chain rollback on the same endpoint can return that head while a previously deployed token still has canonical code. A prior native deployment receipt makes the line 142 check network-only. The historical Core code check in the frozen version would see empty code before Core deployment. An explicit funding nonce then requires only a live network check during initialized preparation at internal/transaction/preparation.go, line 369. Compare the captured number to the deployment floor before using the receipt. This needs no extra RPC.
